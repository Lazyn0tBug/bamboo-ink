# 古籍内容管道重构需求文档

> 状态：草案
> 创建日期：2026-04-11
> 来源：/ce:brainstorm 会话结论

## 1. 问题陈述

当前 JSON IR 管道使用 per-tag cheerio 分类器逐元素判断类型（9 种内容类型），面临以下根本性问题：

1. **结构脆弱**：HTML 源文件由 MS FrontPage 4.0 生成，嵌套结构不可预测（如 `<div align="center">` 包裹 `<table>` 再包裹 `td.swy1`）。每遇到新结构都需要修规则。
2. **规模爆炸**：古籍总量 9000+ 文件（不仅 经部 250 个），每种模板变体都靠规则覆盖不可持续。
3. **AI 成本**：直接把原始 HTML 给 AI 处理，token 消耗大、噪音高、出错概率高。
4. **编码混乱**：源文件混用 GBK 和 UTF-8，每次读取都要猜测编码。
5. **索引缺失**：9000+ 文件没有统一检索入口，增量处理和全量搜索都困难。

## 2. 设计原则

1. **简化优先于 AI**：先用代码做预处理和简化，再给 AI 训练和整理。节约成本，减少 AI 出错概率。
2. **领地式串行提取**：每次只解决一个问题，已认领区域标记跳过，后续自动排除。消除规则冲突。
3. **规则引擎为主，AI 为辅**：90% 文件用规则引擎处理，5-10% 复杂文件 fallback 到 AI。
4. **渐进式架构**：先实现核心功能，再逐步增强。AI 目录-内容自动关联（Component D）暂不实现。
5. **容错优先**：无法分类的内容降级为 `main-text`，不报错、不中断。
6. **最小内容类型**：聚焦核心类型，减少分类边界模糊。

## 3. 四层架构

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: 预处理层（纯代码）                          │
│  - 编码统一转换 (GBK → UTF-8)                        │
│  - HTML 规范化 (FrontPage 标签 → 标准 HTML5)          │
│  - HTML 简化 (表格展平、冗余标签剔除)                   │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  Layer 2: 提取层（规则引擎 + AI Fallback）             │
│  - 规则引擎：90% 文件，基于属性/模式/结构的分类器         │
│  - AI Fallback：5-10% 规则无法处理的复杂文件             │
│  - 容错：无法识别 → main-text                          │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  Layer 3: AI 验证层（批量）                            │
│  - 抽检规则引擎输出的质量                               │
│  - 识别规则引擎未捕获的模式                            │
│  - 反馈优化规则引擎                                     │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│  Layer 4: 索引层                                      │
│  - JSON 目录索引文件（9000+ 文件检索入口）               │
│  - 预留 SQLite 接口（后续全文搜索）                      │
└─────────────────────────────────────────────────────┘
```

### 3.1 Layer 1: 预处理层

**目标**：将 9000+ 源文件统一为干净、一致的 HTML 输入。

| 子模块 | 职责 | 输出 |
|--------|------|------|
| 编码转换器 | 检测并转换 GBK → UTF-8 | UTF-8 HTML |
| HTML 规范化器 | `<center>` → `<div data-center>`、`<font>` → `<span>` | 标准 HTML5 |
| HTML 简化器 | 表格展平、嵌套 div 合并、空标签剔除 | 扁平化 HTML |

**关键决策**：
- 编码转换是一次性操作，不纳入日常管道
- 规范化/简化是每步管道的入口预处理
- 简化后的 HTML 大幅降低 AI 处理的 token 成本

### 3.2 Layer 2: 提取层 — 领地式串行提取

**目标**：从简化后的 HTML 提取结构化内容。

**核心策略**：每次只解决一个问题，已认领区域标记跳过，后续提取自动排除。

#### 3.2.1 提取顺序

9 种内容类型对应 9 个 Pass，每种类型独立一轮，消除一切规则竞争：

```
HTML (已规范化+简化)
  │
  ▼ Pass 1: 发现标题 (book-title)
  │   识别：书名、朝代、作者、序言标题
  │   规则: center + #FF6666/FF0000 + SIZE≥5, class=article
  │   标记区域 [B1], [B2]... → 后续 Pass 跳过
  │
  ▼ Pass 2: 发现元数据 (metadata)
  │   识别：朝代·作者标记（如 "宋·朱熹"）
  │   规则: text pattern "(朝代·作者)", class=metadata
  │   跳过 [B*]... → 标记 [M1]
  │
  ▼ Pass 3: 发现章节 (chapter-title)
  │   识别：章节标记、篇名
  │   规则: #CC33CC, class=chapter, 居中+嵌套font
  │   跳过 [B*],[M*]... → 标记 [C1], [C2]...
  │
  ▼ Pass 4: 发现注疏 (annotation)
  │   识别：集注、夹注、双行小注
  │   规则: font-size=9pt, class=annotation, #551A8B
  │   跳过 [B*],[M*],[C*]... → 标记 [A1], [A2]...
  │
  ▼ Pass 5: 发现段落标记 (section-summary)
  │   识别："右传之X章"、"右经X章"
  │   规则: SECTION_SUMMARY_RE 文本模式
  │   跳过已认领区域 → 标记 [S1], [S2]...
  │
  ▼ Pass 6: 发现结束标记 (end-marker)
  │   识别："仪礼终"、"周易終"
  │   规则: END_MARKER_RE 文本模式
  │   跳过已认领区域 → 标记 [E1]
  │
  ▼ Pass 7: 发现碑文/后记 (colophon)
  │   识别：出版信息、整理者标记
  │   规则: "----------------YOUTH整理" 等模式
  │   跳过已认领区域 → 标记 [L1]
  │
  ▼ Pass 8: 发现导航项 (nav-item)
  │   识别：目录页链接项（仅 catalog 页面）
  │   规则: <a href> in catalog context
  │   跳过已认领区域 → 标记 [N1]...
  │
  ▼ Pass 9: 发现正文 (main-text)
      规则: 无。未 claim 的所有文本节点 = main-text
      （不需要规则判断，剩余即正文）

▼ Pass 10: Fallback 评估
    质量评分 → 低于阈值 → AI Fallback
    未认领区域 → main-text（默认容错）
```

**为什么是这个顺序**：
1. 标题最显眼（颜色、字号、位置），规则最确定，先处理
2. 元数据紧随其后（短文本，易识别）
3. 章节标题次之（通常有固定模式如 `#CC33CC` 色）
4. 注疏通常包裹在正文中（如集注夹在经文间），先剥离注疏才能准确切分正文
5. 段落标记是正文内的结构标记，在注疏剥离后识别更精确
6. 结束标记是边界信号，提前识别防止后续内容被误收
7. 碑文/后记在结束标记之后，隔离出版信息
8. 导航项只在 catalog 页面有意义
9. 正文 = 剩余部分，不需要规则——这是最大简化
10. Fallback 兜底

#### 3.2.2 领地标记机制

每轮提取产出一组 **region 标记**，后续轮次自动跳过：

```
claimed: Set<Node>  // 已被认领的 DOM 节点（元素 + 文本节点）

Pass 1 后: claimed 包含所有 book-title 节点及其后代
Pass 2 后: claimed 包含 metadata 节点
Pass 3 时: 扫描时跳过 claimed 中的节点
...
Pass 9 时: 所有未 claim 的文本节点 = main-text（不需要规则）
```

**优势**：
- **消除规则冲突**：不会再把标题误判为正文，因为标题区域已被标记
- **逐步降噪**：每轮提取后，下一轮的扫描空间缩小、噪音减少
- **可独立测试**：每轮提取独立验证，出问题只修对应 Pass
- **「剩余即正文」**：Pass 4 不需要任何规则，极大简化

#### 3.2.3 规则引擎 vs AI Fallback

**规则引擎**（Pass 1-9）：
- 每轮提取使用独立的规则集，互不干扰
- 9 种类型对应 9 个 Pass，每 Pass 只关心一种类型
- 规则集可被 Book Profile 动态增强（见 §3.5）
- 容错：某轮提取为空，不影响后续轮次

**AI Fallback**（Pass 10 触发）：
- 触发条件：规则引擎总产出质量低于阈值
  - 0 chapters（文件明显有章节结构）
  - 0 annotations（文件有明显注疏标记）
  - 单章节包含全部内容（规则未生效的信号）
  - 提取内容显著低于同书平均（Book Profile 比较）
- 输入：简化后的 HTML（token 成本降低 60-80%）
- 输出：与规则引擎相同的 JSON IR 格式
- 结果缓存：AI 结果持久化，避免重复调用

### 3.3 Layer 3: AI 验证层

**目标**：批量验证规则引擎的产出质量，发现未覆盖的模式。

- 随机抽检 5-10% 的规则引擎产出
- 对比 AI 独立提取的结果
- 产出覆盖率报告：哪些模式规则引擎漏掉了
- 反馈：报告驱动规则引擎迭代

### 3.4 Layer 4: 索引层

**目标**：为 9000+ 文件提供统一检索入口。

### 3.5 Book Profile 系统（新增）

**目标**：利用「同一本书的所有内容文件共享同一套 FrontPage 模板」这一不变性，建立 Book Profile 动态增强规则。

**工作机制**：
1. 处理一本书的第一个文件时，规则引擎用硬编码默认规则提取
2. 提取成功后，从结果中分析出 Book Profile：
   - `chapterColors`: 该文件实际使用的章节颜色（如 `["#CC33CC"]`）
   - `bookTitleColors`: 标题颜色（如 `["#FF6666"]`）
   - `annotationSizes`: 注疏字号（如 `[9]`）
   - `annotationColors`: 注疏颜色（如 `["#551A8B"]`）
   - `contentContainer`: 内容容器 selector（如 `"div.swy1"`）
   - `hasSwy1`: 是否包含 swy1 容器
3. 处理同书的后续文件时，Pass 规则用 Profile 数据增强：
   - Pass(chapter-title): 不仅匹配 `#CC33CC`，还匹配 Profile 中发现的其他章节颜色
   - Pass(annotation): 不仅匹配 9pt，还匹配 Profile 中的其他注疏字号
4. Book Profile 持久化到磁盘缓存（`.pipeline-cache/profiles/<book>.json`），跨运行复用

**收益**：
- 规则从「猜可能出现的颜色」变为「已知这本书实际使用的颜色」
- 对模板变体（同一书的不同文件有细微差异）更鲁棒
- 同书后续文件处理速度提升 60%+（规则匹配范围缩小）

### 3.6 DOM 一次索引优化（新增）

**目标**：避免 9 个 Pass 各自全量扫描 DOM 造成的 O(9n) 性能浪费。

**机制**：
1. 在 cheerio.load() 后，执行一次 DOM 遍历，建立索引：
   - `byColor`: `Map<color, Node[]>` — 按 color 属性索引
   - `byClass`: `Map<class, Node[]>` — 按 class 属性索引
   - `byTag`: `Map<tagName, Node[]>` — 按标签名索引
   - `bySize`: `Map<size, Node[]>` — 按 font size 索引
   - `allTextNodes`: `Node[]` — 所有文本节点
2. 9 个 Pass 在索引 Map 上查询，不再遍历 DOM
3. 总复杂度从 O(9n) 降到 O(n + 9k)，k 为匹配结果数（通常 << n）

### 3.7 HTML 规范化约束（新增）

**关键约束**：规范化只做结构层，不碰语义标签。

- ✅ 允许：表格展平、`<center>` → `<div data-center>`、空标签剔除
- ❌ 禁止：`<font>` → `<span>`、`<b>` → `<strong>` 等标签替换

**理由**：提取规则依赖 `<FONT color=...>` 等标签名和属性。规范化改变标签名等于同时改变输入格式和提取规则，两个变量同时变会倍增调试难度。等提取稳定后再考虑标签规范化。

### 3.8 Layer 4: 索引层（原文档 §3.4）

**目标**：为 9000+ 文件提供统一检索入口。

**阶段 1 — JSON 索引文件**：
```json
{
  "version": 1,
  "books": [
    {
      "id": "经部/大学章句集注",
      "title": "大学章句集注",
      "category": "经部",
      "chapters": ["大学之道", "诚意", "正心"],
      "irPath": "src/content-ir/经部/大学章句集注.json",
      "mdPath": "src/content/guji/经部/大学章句集注.md",
      "wordCount": 15460,
      "processedAt": "2026-04-11T12:00:00Z"
    }
  ]
}
```

**阶段 2 — 预留 SQLite 接口**：
- 全文搜索（按关键词检索古籍内容）
- 分类检索（按四部分类筛选）
- 统计查询（覆盖率、处理状态）

## 4. 内容类型定义

采用完整 9 种内容类型，每种类型对应一个独立 Pass：

| 类型 | Pass | 含义 | 示例 |
|------|------|------|------|
| `book-title` | 1 | 全书标题 | "大学章句集注" |
| `metadata` | 2 | 朝代·作者标记 | "宋·朱熹" |
| `chapter-title` | 3 | 章节标题 | "大学之道"、"诚意" |
| `main-text` | 9 | 正文内容 | 经文正文 |
| `annotation` | 4 | 注释/集注 | 朱熹集注、程子注 |
| `section-summary` | 5 | 段落总结标记 | "右传之首章，释明明德" |
| `end-marker` | 6 | 结束标记 | "仪礼终" |
| `colophon` | 7 | 碑文/后记 | "----------------YOUTH整理" |
| `nav-item` | 8 | 导航项 | 目录页链接 |

**说明**：
- 9 Pass = 9 类型，一一对应，消除一切规则竞争
- 无法分类的默认归入 `main-text`（容错策略）

## 5. 非功能性需求

| 需求 | 目标 | 测量方式 |
|------|------|----------|
| 覆盖率 | 90%+ 文件规则引擎可处理 | Layer 3 抽检报告 |
| 容错率 | 0 文件因分类失败而跳过 | 管道日志统计 |
| AI 成本 | 仅 5-10% 文件调用 AI | API 调用计数 |
| 增量处理 | 支持单文件/单类别处理 | CLI 参数验证 |
| 索引构建 | 全量索引 < 30s | 构建时间测量 |

## 6. 实现优先级

按 Pass 顺序逐步实现，每步独立验证：

| 阶段 | 内容 | 依赖 |
|------|------|------|
| P0 | 编码转换器（一次性脚本） | 无 |
| P1 | HTML 规范化 + 简化器（只做结构层）+ DOM 一次索引 | P0 |
| P2a | Pass 1: book-title | P1 |
| P2b | Pass 2: metadata | P2a |
| P2c | Pass 3: chapter-title | P2b |
| P2d | Pass 4: annotation | P2c |
| P2e | Pass 5: section-summary | P2d |
| P2f | Pass 6: end-marker | P2e |
| P2g | Pass 7: colophon | P2f |
| P2h | Pass 8: nav-item | P2g |
| P2i | Pass 9: main-text（剩余即正文） | P2h |
| P2j | Pass 10: Fallback 评估 + Book Profile 系统 | P2a-P2i |
| P3 | JSON 索引构建 | P2j |
| P4 | AI Fallback 机制 | P2j |
| P5 | AI 验证层（抽检） | P4 |
| P6 | SQLite 接口 | P3 |

## 7. 排除范围

以下功能明确**不在此阶段实现**：

- **Component D**：目录页与内容页的自动关联（目录树构建后独立处理）
- **全文搜索 UI**：仅预留 SQLite 接口，前端搜索后续实现
- **AI 全自动提取**：AI 仅作为 fallback 和验证工具，不替代规则引擎

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 编码检测不准 | 乱码输出 | 检测失败时保留原编码并记录警告 |
| AI Fallback 不稳定 | 产出格式不一致 | 严格 JSON Schema 校验，不合格则降级为 main-text |
| 简化过度 | 丢失结构信息 | 保留原始 HTML 备份，简化只做结构不做语义 |
| 9000+ 文件处理时间长 | 构建慢 | 增量处理 + 缓存机制 |
| 早期 Pass 误标区域 | 后续 Pass 无法纠正 | 领地标记支持降级/撤销机制；AI 验证层反馈修正 |
| Pass 顺序不合理 | 某些模式被错误归类 | 通过 AI 验证层的覆盖率报告持续调整顺序 |
